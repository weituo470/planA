# MVP3 需求（requirements）

## 背景
目前 Dashboard 已支持生成 `tasks.md` 并进一步原子化生成 `tasks_atomic.md`，但原子任务只能以只读文本查看，无法一键触发“对某条原子任务进行开发”的 Codex CLI 工作流。

## 目标
- 在 Dashboard 的“原子任务（tasks_atomic）”视图中，将每条原子任务结构化展示，并为每条任务提供“开始”按钮。
- 点击“开始”后，由 Bridge 在本机调用 Codex CLI，使用该原子任务作为输入，启动一次针对该任务的开发执行。
- 每次启动前生成一份“任务执行文档”并落盘到指定文件夹，作为可追溯的执行上下文与输入源。

## 非目标
- 不实现完整的交互式终端（输入/中断/多会话管理）能力；本期以“启动一次非交互式执行 + 观察输出”为主。
- 不做复杂权限/鉴权体系（默认本地内网/单机使用）。

## 用户故事
- 作为使用者，我希望在 `tasks_atomic` 里看到结构化任务卡片，并可以对任意一条点击“开始”，自动调用 Codex CLI 来实现这条任务。
- 作为使用者，我希望每次执行都会生成一份独立的任务文档，后续可以回溯该次执行输入与结果摘要。

## 功能需求
### FR1 原子任务结构化展示
- 当用户在 Dashboard 选择 `tasks` → `原子任务` 视图时，系统应解析 `tasks_atomic.md` 的任务块，并以列表/卡片形式展示：
  - Task 编号（如 `Task 1.2`）
  - title / core / details / ac
  - 完成状态（`[ ]`/`[x]`）

### FR2 原子任务“开始”按钮
- 当用户点击某条原子任务的“开始”按钮时，系统应调用 Bridge 的 API，触发 Codex CLI 执行该任务。
- 如果任务不存在/解析失败/文件缺失，应在 UI 给出可读错误提示。

### FR3 任务执行文档落盘
- 每次点击“开始”时，Bridge 应生成任务执行文档并写入文件夹（每次执行一个文件）：
  - 包含 spec 名称、任务编号、任务四字段、执行时间
  - 给出上下文入口（例如 `workflow/specs/<spec>/requirements.md` 等）

### FR4 运行可见性（最小化）
- Dashboard 应提供最小可见性：展示 Bridge 的当前状态（例如 `Executing/Thinking`）与最近输出日志（用于观察 Codex 运行进度）。

## 验收标准（EARS）
- 当 `tasks_atomic.md` 存在且包含原子任务块时，系统应在 Dashboard 中展示每条原子任务的结构化卡片，并显示“开始”按钮。
- 当用户点击某条原子任务的“开始”按钮时，系统应在 Bridge 侧生成任务执行文档文件，并启动一次 Codex CLI 执行；Dashboard 应提示已启动并展示运行状态/日志可见。
- 当 `tasks_atomic.md` 缺失或不包含指定任务时，系统应拒绝启动并返回明确错误信息。
