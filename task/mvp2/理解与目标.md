# MVP2 理解与目标（复刻 Kiro Spec 模式）

## 背景理解
Kiro 的 Spec 模式核心在于将开发流程固化为三份结构化工件，并通过阶段化推进来确保需求、设计与执行的一致性：
- `requirements.md`：用户故事与验收标准（EARS 结构）
- `design.md`：技术架构、序列流程、实现考虑
- `tasks.md`：可追踪的任务拆解与执行状态

## 资料来源与限制
- 官方文档当前无法访问（网络拉取失败），以下理解基于既有公开认知与现有实现形态。
- 后续可在可访问时补充“阶段门控/模板字段”等细节。

## MVP2 目标
在浏览器中复刻 Kiro 的 Spec 体验，实现最小可用闭环：
- 支持 Spec 列表与选择
- 支持三份文档的查看与编辑
- 支持一键创建 Spec 并生成模板
- 明确文档顺序与确认（需求 → 设计 → 任务）
- 与现有事件流/日志/DAG 面板并存，不破坏 MVP1

## MVP2 范围（最小化实现）
- Spec 列表（来自本地 `workflow/specs/`）
- Spec 文件 CRUD（requirements/design/tasks）
- 三阶段标签切换（Requirements / Design / Tasks）
- 顺序确认：需求确认后解锁设计，设计确认后解锁任务
- 保存后自动写入文件并触发 Diff 监听

## 不做（MVP2 外）
- 自动生成设计图/序列图
- spec 与任务 DAG 的强绑定
- 权限与多用户协作
- PBT（性质测试）自动化

## 当前实现状态
- Bridge 已提供 Spec 列表/创建/读取/保存/确认 API。
- Dashboard 已提供 Spec 面板（列表、三文档切换、保存、确认）。
- Spec 默认根目录为 `workflow/specs/`。

## 下一步检查点
- 启动 Bridge/Dashboard 后，浏览器完成新建/编辑/确认闭环验证。
- 确认后按顺序解锁下一文档，日志中出现 `[spec] confirmed ...`。
- 保存触发 Diff 预览，日志中出现 `[spec] saved ...`。

## 验收标准
- 新建 Spec 后，requirements 自动创建
- 确认 requirements 后生成 design，确认 design 后生成 tasks
- 在浏览器中编辑并保存，文件内容实时更新
- 文件更新后，Diff 侧栏可看到变化
